# Mini MMO 서버

여러 사람이 브라우저로 접속해 같은 마을을 돌아다니는 작은 MMO의 게임 서버입니다. C++17과 운영체제의 소켓 기능만으로 만들었고 외부 라이브러리가 없습니다 (macOS, Linux).

이 문서는 서버가 **돌아가기 위해 꼭 필요한 동작**만 설명합니다. 접속하고, 로그인하고, 월드에 들어가 움직이고, 그 모습이 다른 사람에게 보이는 것까지입니다. 하우징, 농장, 미니게임 같은 콘텐츠는 이 뼈대 위에 얹힌 것이라 여기서는 다루지 않습니다. 프론트엔드를 새로 만드는 사람을 위해 서버와 주고받는 메시지 형식도 함께 적었습니다.

## 빌드와 실행

```bash
cd server
make                 # server/mmo_server 가 만들어진다
./mmo_server 8080 ../client ./data
```

세 인자는 차례로 포트, 정적 파일 폴더, 데이터 폴더입니다. 서버는 같은 포트에서 정적 파일(HTTP)과 게임 연결(WebSocket)을 함께 받습니다. 프론트엔드를 따로 만든다면 두 번째 인자에 그 빌드 폴더를 주어 서버가 같이 서빙하게 하거나, 프론트엔드를 다른 곳에 올리고 WebSocket만 이 서버로 붙이면 됩니다. 서버는 접속한 페이지의 출처(`Origin`)를 검사하지 않으므로 어느 주소의 페이지에서도 연결할 수 있습니다.

데이터 폴더에는 계정 파일이 쌓입니다. 폴더를 지우면 모든 계정이 사라진 깨끗한 상태로 시작합니다.

## 서버가 하는 일

서버는 프로그램 하나이고, 모든 플레이어가 그 프로그램의 메모리에 있는 월드 하나를 함께 씁니다. 서버는 1초에 20번 월드를 한 칸씩 진행시키는데, 이 한 칸을 **틱(tick)**이라고 부릅니다. 브라우저는 "어느 방향키를 누르고 있다" 같은 입력만 보내고, 캐릭터가 실제로 어디에 있는지는 서버가 정합니다. 화면을 그리는 일은 서버가 하지 않습니다. 서버는 위치를 계산해 보내기만 하고, 그림은 프론트엔드가 그립니다.

이 일은 네 부분으로 나뉩니다.

### 1. 연결

브라우저와 서버는 **WebSocket**으로 연결됩니다. 웹페이지의 보통 요청과 달리 연결이 계속 열려 있어서, 양쪽이 언제든 메시지를 보낼 수 있습니다.

이 일은 `server/src/base/ws_server.*`가 맡습니다. 여러 연결을 한 스레드에서 번갈아 살피고(`poll`), 메시지가 오면 게임 쪽(`Game::onMessage`)에 넘기며, 연결이 끊기면 그것도 알립니다(`Game::onClose`). 연결마다 번호(`ConnId`)가 붙고, 게임 쪽은 이 번호로 누구에게 보낼지를 정합니다. 이 부분은 게임 내용을 모릅니다. 글자를 받고 넘기는 일만 합니다.

서버의 심장은 `server/src/main.cpp`의 루프입니다. 다음 틱 시각이 될 때까지 네트워크 메시지를 처리하다가, 시각이 되면 `game.tick()`을 불러 월드를 1/20초만큼 진행시키는 일을 반복합니다. 메시지 처리와 게임 진행이 같은 스레드에서 차례로 일어나므로 게임 상태에는 잠금이 필요 없습니다.

### 2. 로그인과 입장

연결은 세 단계를 거칩니다. 처음에는 아무것도 아닌 연결이고, 로그인하면 계정이 붙은 연결이 되고, 캐릭터를 정해 입장하면 월드 안의 플레이어가 됩니다. 입장하기 전에는 로그인과 입장 메시지 말고는 모두 무시합니다. 이 과정은 `server/src/core/session.cpp`에 있습니다.

로그인은 아이디와 비밀번호를 받습니다. 처음 보는 아이디면 그 자리에서 가입시킵니다. 비밀번호는 원문을 저장하지 않고 PBKDF2로 60만 번 섞은 결과만 저장합니다. 이 계산은 일부러 느리게 만든 것이라 작업 스레드(`server/src/base/worker.hpp`)에 맡기고, 끝나면 결과만 메인 루프로 돌려받습니다. 한 계정은 한 곳에서만 접속할 수 있어서, 같은 계정으로 새로 로그인하면 이전 연결은 끊깁니다.

로그인에 성공하면 서버는 **이어 들어오기 표**를 줍니다. 서버만 아는 열쇠로 서명한 30일짜리 문자열로, 연결이 끊기거나 서버가 다시 켜져도 이 표로 비밀번호 없이 다시 로그인할 수 있습니다. 구조는 JWT와 같습니다.

입장은 캐릭터의 색, 팔·다리 모양, 이름을 받아 월드에 넣는 단계입니다. 계정에 저장된 마지막 위치가 아직 설 수 있는 곳이면 거기에, 아니면 마을 광장 근처의 빈 곳에 세웁니다.

계정은 `server/src/core/accounts.*`가 관리합니다. 데이터 폴더에 계정마다 텍스트 파일이 하나씩 있고, 서버를 켤 때 전부 메모리로 읽어 둡니다. 위치와 모양은 퇴장할 때, 서버를 끌 때, 접속 중에는 20초마다 파일에 씁니다. 임시 파일에 먼저 쓰고 이름을 바꾸는 방식이라, 쓰는 도중에 서버가 죽어도 이전 파일이 남습니다.

### 3. 월드와 이동

월드의 모양은 `server/src/core/world.*`에 있습니다. 강, 다리, 건물, 지나갈 수 없는 영역(충돌 영역)이 여기서 정해지고, 서버를 켤 때 한 번 만들어집니다. 월드는 **구역(zone)**으로 나뉩니다. 0번이 마을이고 1번부터는 건물 안입니다. 같은 구역에 있는 사람끼리만 서로 보입니다. 문 앞에서 문을 쓰면 그 문이 이어진 구역으로 옮겨집니다.

움직임은 이렇게 처리됩니다. 프론트엔드는 방향키를 누르거나 뗄 때마다 지금 눌린 방향들을 숫자 하나로 묶어 보냅니다. 서버는 그 값을 기억만 해 두고, 틱마다 그 방향으로 1/20초 동안 갈 거리(초당 220px)만큼 캐릭터를 옮깁니다. 대각선으로 갈 때는 더 빨라지지 않게 보정합니다. 위치가 아니라 방향만 받기 때문에 프론트엔드가 속도를 조작하거나 순간이동할 수 없습니다.

옮기기 전에는 `World::move`가 충돌을 확인합니다. 가려는 곳이 강물이거나 충돌 영역 안이면 그쪽으로는 가지 않고, 가로와 세로를 따로 확인해서 벽에 비스듬히 부딪히면 벽을 따라 미끄러집니다.

### 4. 보내기

서버는 매 틱이 끝날 때(`server/src/core/send.cpp`의 `broadcastState`) 각 구역에 있는 모든 플레이어의 번호, 위치, 색, 이름을 그 구역 사람들에게 보냅니다. 프론트엔드는 이 메시지를 받아 사람들을 그립니다. 보내는 범위는 한 사람, 한 구역(`sendToZone`), 모두(`sendToAll`) 세 가지입니다. 위치는 같은 구역에만, 채팅과 입장·퇴장 안내는 모두에게 갑니다.

## 프론트엔드를 따로 만들 때

### 주고받는 방식

- 주소: `ws://<서버>:<포트>/ws` (운영에서는 TLS를 붙여 `wss://`). 서버는 경로를 보지 않지만 `/ws`를 쓰는 것을 권합니다.
- **프론트엔드 → 서버**: 텍스트 한 줄. 첫 공백 앞이 명령이고 뒤가 인자입니다. 모르는 명령과 형식이 틀린 요청은 조용히 무시됩니다.
- **서버 → 프론트엔드**: JSON 객체 하나. `t`가 종류입니다. 아래 표에 없는 종류(콘텐츠용)가 와도 무시하면 됩니다.

### 꼭 필요한 메시지

| 방향 | 메시지 | 뜻 |
|---|---|---|
| → 서버 | `login <아이디> <비밀번호>` | 로그인. 없는 아이디면 가입. 아이디는 2~20자의 한글·영문·숫자·`_`·`-`, 비밀번호는 4~128바이트 |
| → 서버 | `resume <표>` | 이어 들어오기 표로 로그인 |
| → 서버 | `join <#rrggbb> <팔> <다리> <팔다리색> <이름>` | 입장. 팔·다리·팔다리색은 0~2. 이름은 공백을 포함해 나머지 전부 |
| → 서버 | `in <방향>` | 지금 누르고 있는 방향. 위 1, 아래 2, 왼쪽 4, 오른쪽 8을 더한 값 (예: 위+오른쪽 = 9, 뗐으면 0) |
| → 서버 | `use door` | 가까운 문(56px 안)으로 들어가거나 나가기 |
| → 서버 | `chat <글>` | 전체 채팅 (200자) |
| 서버 → | `{"t":"auth","ok":true,"new","id","nick","rt",...}` | 로그인 성공. `rt`가 이어 들어오기 표. 실패하면 `{"t":"auth","ok":false,"m":"까닭"}` |
| 서버 → | `{"t":"kick","m"}` | 다른 곳에서 같은 계정으로 로그인해 끊김 |
| 서버 → | `{"t":"welcome","id","w","h","speed","tick",...}` | 입장 승인. `id`가 내 연결 번호 (state 에서 나를 찾을 때 씀) |
| 서버 → | `{"t":"map",...}` | 월드 지도 (입장할 때 한 번). 아래 「지도」 참고 |
| 서버 → | `{"t":"zone","z","x","y"}` | 내 구역과 위치가 바뀜 (입장, 문) |
| 서버 → | `{"t":"state","k","on","p":[...]}` | 매 틱. `k` 틱 번호, `on` 접속자 수, `p` 같은 구역 사람들 `{"id","x","y","c":"#rrggbb","n":"이름"}` |
| 서버 → | `{"t":"chat","id","n","c","m"}` | 채팅 |
| 서버 → | `{"t":"sys","m"}` | 안내 문구 (입장·퇴장, 오류) |

`state`의 사람 항목에는 해당할 때만 붙는 값도 있습니다. `d`는 누르고 있는 방향, `a`는 모양(팔 + 다리×3 + 팔다리색×9), `s`는 앉은 자리 번호+1입니다. 없으면 0으로 보면 됩니다.

### 지도

`map` 메시지에서 뼈대에 필요한 것은 아래와 같습니다. 나머지 필드는 콘텐츠용이라 무시해도 됩니다.

- `zones`: 구역 목록. 번호가 곧 구역 번호입니다. `{"w","h","door":[x,y]}`에서 `w`, `h`는 크기, `door`는 건물 안 구역의 나가는 문 자리입니다.
- `buildings`: 마을의 건물. `{"k","name","x","y","halfW","back","front","door":[x,y],"room"}`. 건물은 바닥 가운데 `(x, y)`에서 좌우 `halfW`, 뒤로 `back`, 앞으로 `front`만큼 차지합니다. `room`은 문으로 들어가는 구역 번호입니다.
- `solids`: 충돌 영역 `[구역, x0, y0, x1, y1]`
- `step`, `top`, `bot`: 마을의 강. x를 `step`(40px) 간격으로 나눈 지점마다 강의 위쪽·아래쪽 둑의 y 값이고, 그 사이를 직선으로 잇습니다. `bridge`는 다리의 양 끝 x입니다.

좌표는 px 단위이고 y는 아래로 커집니다. 캐릭터의 위치는 발밑 가운데입니다.

### 그리는 방법

가장 단순한 프론트엔드는 `state`가 올 때마다 받은 위치에 사람들을 그리는 것입니다. 이것만으로도 동작하지만, 1초에 20번만 위치가 와서 움직임이 끊겨 보입니다. 보통은 두 가지를 더합니다.

- **보간**: 다른 사람은 이전 위치와 새 위치 사이를 화면 프레임마다 이어 그립니다.
- **예측**: 내 캐릭터는 키를 누르는 즉시 같은 규칙(초당 220px, 같은 충돌)으로 먼저 움직여 보이고, `state`가 오면 어긋난 만큼 맞춥니다. 예측을 빼면 키 반응이 회선 지연만큼 늦게 보입니다.

### 가장 작은 예

```js
const ws = new WebSocket(`ws://${location.hostname}:8080/ws`);
const people = new Map();
let myId = null, keys = 0;

ws.onopen = () => ws.send('login ctfuser secret123');
ws.onmessage = (event) => {
  const msg = JSON.parse(event.data);
  if (msg.t === 'auth' && msg.ok) ws.send('join #ff8899 1 1 0 해커');
  else if (msg.t === 'auth') console.log('로그인 실패:', msg.m);
  else if (msg.t === 'welcome') myId = msg.id;
  else if (msg.t === 'state') {
    people.clear();
    for (const p of msg.p) people.set(p.id, p);   // 이 위치에 그린다. 나는 p.id === myId
  } else if (msg.t === 'chat' || msg.t === 'sys') console.log(msg.n ?? '', msg.m);
};

const BITS = { ArrowUp: 1, ArrowDown: 2, ArrowLeft: 4, ArrowRight: 8 };
const press = (code, down) => {
  if (!BITS[code]) return;
  const next = down ? keys | BITS[code] : keys & ~BITS[code];
  if (next !== keys) ws.send(`in ${keys = next}`);   // 바뀔 때만 보낸다
};
addEventListener('keydown', (e) => press(e.code, true));
addEventListener('keyup', (e) => press(e.code, false));
```

## 커스텀할 때 알아 둘 것

### 새 명령 더하기

1. `server/src/core/game.hpp`의 `Game` 클래스에 처리 함수를 선언합니다.
2. 함수 본문은 `.cpp` 파일에 씁니다. 파일 첫 줄에 `#include "core/rules.hpp"`를 넣습니다. Makefile은 `server/src` 아래의 `.cpp`를 모두 찾아 빌드하므로 고칠 필요가 없습니다.
3. `server/src/core/game.cpp`의 `onMessage`에 `else if (cmd == "새명령") 함수(id, p, arg);`를 한 줄 더합니다. `p`는 보낸 플레이어이고 `arg`는 명령 뒤의 글자 전체입니다.
4. 답은 `server_.send(id, json)`(그 사람에게), `sendToZone(p.zone, json)`, `sendToAll(json)`으로 보냅니다. JSON에 사용자가 보낸 글을 넣을 때는 `text::jsonEscape`를 거칩니다.
5. 틱마다 할 일이 있으면 `Game::tick`에서 부릅니다.

### 믿어도 되는 것과 아닌 것

서버가 정하는 값은 위치, 구역, 계정 정보이고, 이것들은 프론트엔드가 바꿀 수 없습니다. 프론트엔드가 보내는 것은 모두 사용자가 마음대로 바꿀 수 있는 입력이므로, 새 명령을 만들 때는 서버에서 범위와 형식을 검사해야 합니다. 기존 코드의 숫자 읽기(`parseWhole`, `clampInt`)와 글 정리(`text::sanitize`, `server/src/base/text.hpp`)를 참고하면 됩니다. 반대로 CTF 문제로 일부러 허점을 만들 때도 이 지점이 손댈 곳입니다.

### 여러 사람이 한 곳에서 접속할 때

서버에는 IP 하나당 제한이 있습니다. 동아리방처럼 여러 명이 같은 공인 IP로 접속하면 걸리므로 행사 전에 환경변수로 늘려 둡니다.

| 환경변수 | 기본값 | 뜻 |
|---|---|---|
| `MMO_SIGNUP_LIMIT` | 10 | IP 하나가 한 시간에 만들 수 있는 계정 수 |
| `MMO_MAX_CONN_PER_IP` | 16 | IP 하나가 동시에 유지할 수 있는 연결 수 |
| `MMO_AUTH_PER_IP` | 3 | IP 하나가 동시에 처리할 수 있는 로그인 수 |
| `MMO_AUTH_ITERATIONS` | 600000 | 새 비밀번호의 해시 반복 횟수. 낮추면 로그인이 빨라지지만 비밀번호가 새었을 때 덜 안전 |

예: `MMO_SIGNUP_LIMIT=200 MMO_MAX_CONN_PER_IP=200 MMO_AUTH_PER_IP=20 ./mmo_server 8080 ../client ./data`

이 밖에 같은 계정에서 연속으로 5번 틀리면 30초 잠그고, 채팅은 초당 1개(한꺼번에 5개)로 제한합니다. 이동 입력(`in`)에는 제한이 없습니다.

### 콘텐츠를 걷어 낼 때

`server/src`의 `home/`, `activity/`, `social/`은 콘텐츠입니다. 이 폴더들만 지우면 빌드가 되지 않습니다. `core/game.cpp`의 `onMessage`와 `tick`, `core/send.cpp`의 `sendRoomStateOnEntry`, `core/session.cpp`의 `join`이 콘텐츠 함수를 부르고 있어서, 그 줄들과 `core/game.hpp`의 선언도 함께 지워야 합니다.
